# Agent 交互确认机制

## 核心原则

**Agent 不应猜测用户意图，而应在关键点停下来确认。**

## 交互触发时机

### 必须交互的场景

| 场景 | 交互方式 | 说明 |
|------|----------|------|
| 任务开始 | AskQuestion 或自然语言 | 输出任务理解 + 执行计划，等待确认 |
| 多方案选择 | AskQuestion | 列出方案优劣，让用户选择 |
| 架构/设计变更 | AskQuestion | 变更前必须确认 |
| 文件删除/大规模重构 | AskQuestion | 列出影响范围，确认后执行 |
| 不确定的需求 | 自然语言提问 | 直接问，不要猜 |
| 阶段性任务完成 | 自然语言汇报 | 输出已完成内容和下一步计划 |

### 不需要交互的场景

- 用户指令明确且无歧义的简单修改
- 已经确认过方案后的具体实现步骤
- 修复明显的编译错误或 typo

## 交互方式优先级

### 优先级 1：AskQuestion（Cursor 内置）

适用于有明确选项的决策点。在聊天窗口内显示，不弹外部窗口。

**使用场景**：方案选择、是/否确认、优先级排序

```
示例：用 AskQuestion 让用户选择方案
- 方案A: 使用继承实现多态
- 方案B: 使用组合+接口
- 方案C: 使用模板泛型
```

### 优先级 2：自然语言对话

适用于需要自由文本回复的场景。Agent 输出问题后结束当前回合，等待用户在聊天框中回复。

**使用场景**：需求澄清、开放式问题、进度汇报等待反馈

**关键**：输出问题后必须**结束回合**（不再调用任何工具），让用户有机会回复。

### 优先级 3：MCP Feedback（仅在规则要求时）

仅当用户的 Cursor Rules 中明确写了"使用 mcp-feedback-enhanced"时才使用。
否则优先使用前两种方式。

## 任务开始流程

收到复杂任务时，按以下流程执行：

1. **分析任务** — 理解用户需求，识别关键决策点
2. **输出计划** — 用 TodoWrite 创建任务列表，并输出给用户看
3. **确认计划** — 用 AskQuestion 或自然语言确认：
   - 任务理解是否正确
   - 执行计划是否合理
   - 是否有遗漏的需求
4. **用户确认后** — 开始执行

## 阶段性汇报模板

每完成一个阶段性任务后，输出以下内容：

```
## 阶段完成汇报

### 已完成
- [具体完成的内容]

### 当前状态
- [编译是否通过/测试结果等]

### 下一步计划
- [接下来要做什么]

### 需要确认
- [如果有需要用户决策的点]
```

然后等待用户反馈后再继续。

## 决策确认模板

遇到多方案选择时，使用 AskQuestion 工具：

```
AskQuestion 参数示例：
- title: "方案选择"
- questions: [{
    id: "approach",
    prompt: "以下哪种方案更符合你的需求？",
    options: [
      { id: "a", label: "方案A: [简述] — 优点/缺点" },
      { id: "b", label: "方案B: [简述] — 优点/缺点" },
      { id: "c", label: "方案C: [简述] — 优点/缺点" }
    ]
  }]
```

## 注意事项

1. **不要过度交互** — 简单明确的任务不需要反复确认，避免打断用户工作流
2. **合并确认点** — 如果连续多个小决策，合并成一次 AskQuestion 多问题
3. **提供默认推荐** — 在选项中标注推荐方案，减少用户决策负担
4. **记住已确认的决策** — 同一对话中已确认过的方案不要重复询问
